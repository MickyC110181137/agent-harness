# 設計取捨

這份文件記錄 harness 裡每條主要規則**為什麼存在**，以及它**付出了什麼代價**。多數規則都不是一開始就想好的，而是在實際使用中踩到問題後才定下來。

長期且難以逆轉的新取捨，依 [`templates/adr.md`](../templates/adr.md) 寫成 ADR。

---

## 1. 狀態只有一個來源

**情境**　計畫、進度紀錄、交接筆記、各 worktree 裡的狀態副本都在描述「現在做到哪」。時間一長，它們各說各話，agent 讀到哪一份就相信哪一份。

**決定**　只有 `feature_list.json` 能表達狀態。其他檔案只記脈絡，衝突時以狀態檔為準。開 worktree 前工作項必須先提交，讓 worktree 以含這筆工作項的狀態為基底，不產生第二份狀態。

**代價**　每次更新都要記得回頭改狀態檔；交接快照、計畫都不能「順便」記狀態，寫起來比較囉嗦。所以需要驗證器（第 3 點）來抓漂移。

---

## 2. 多個 repo 共用一套集中式 harness

**情境**　起初每個產品 repo 各有一套 harness。一個跨兩三個 repo 的工作項，要在兩三份狀態檔之間手動對齊；各 repo 的規則也逐漸分歧。

**決定**　狀態、規範、計畫、完成紀錄與各 repo 的技術文件全部收進一個 harness 根目錄。產品 repo 只保留原始碼與自己的驗證入口。唯一鍵改成 `(project, id)`。

**代價**
- **技術文件與程式碼分屬不同 repo**，無法在同一個 commit 一起更新，長期可能漂移。
- **沒有任何單一 commit 能涵蓋一個工作項**：程式碼在產品 repo 的分支，狀態在 harness repo。因此多了一條硬性順序——**分支必須先合併回主線，才可以把工作項標成 `pass`**。
- **只 clone 單一產品 repo 的環境（例如 CI）拿不到 harness**，所以產品 repo 的驗證入口不能依賴 harness 的驗證器。

---

## 3. 能機械判定的交給腳本，其餘交給清單

**情境**　規則全寫在文件裡時，欄位缺漏、路徑失效、同一棵 worktree 被兩筆工作項認領，人眼每次都有機會漏看。

**決定**　狀態不變式由一支**無第三方依賴**的驗證器檢查，失敗時非零結束，診斷指到工作項與規則。判斷不了的部分（證據夠不夠、完成條件是否真的滿足）留給收尾清單與評分表。驗證器的實作語言不限，用專案既有的工具鏈即可。

**代價**　驗證器本身也要維護；規則表與文件要保持一致。有些欄位經過討論後刻意**不**強制，避免驗證器變成阻礙正常工作的官僚。

---

## 4. 進行中的上限由 worktree 決定，不是固定數字

**情境**　「同時只能有一個進行中」在單一 repo 時很合理，但跨 repo 的工作項天生就要同時動兩個檢出，而兩個互不相關的工作項平行也不衝突。

**決定**　不設固定上限，改由兩條結構性規則推導：**沒有 worktree 就不能 `in-progress`**，**一棵 worktree 只能被一筆工作項認領**。上限自然等於真實存在的 worktree 數。

**代價**　純文件或 harness 本身的維護不開 worktree，因此即使正在做也不能標 `in-progress`，只能停在 `not-started` 直到收尾——這在語意上有點反直覺。

---

## 5. 拆票與實作由人觸發

**情境**　agent 很擅長「把事情做下去」，包括在方向錯誤時也做下去，或在失敗時反覆重試。

**決定**　`to-tickets` 與 `implement` 設定 `disable-model-invocation: true`，agent 呼叫一定被擋。agent 負責把前置準備做到位（同步、狀態、worktree、baseline、計畫審計），然後停下，由人輸入指令啟動。`diagnosing-bugs` 則允許 agent 自行呼叫，因為診斷不會改變範圍或主線。

**代價**　流程在這兩個點一定會等人，無法完全無人值守。這是刻意的：拆票決定範圍、實作決定什麼會進主線，這兩個承諾點值得人花那幾秒確認。

---

## 6. 驗證必須在部署後的環境做

**情境**　在本機跑分支程式碼、連到測試環境的資料庫，測起來一切正常；部署上去才發現設定、權限或路由不同。

**決定**　服務端改動一律部署到測試環境，**對部署後的服務**驗證；明文禁止用本機分支程式碼連線測試環境來代替。

**代價**　每次驗證都要走一次部署，回饋迴圈變長。靜態與單元測試因此更重要，要在部署前把能抓的問題抓完。

---

## 7. 證據必須可追溯，不適用也要寫出來

**情境**　「已驗證」「測試通過」這類敘述無法被檢查，也分不出是真的跑過還是覺得應該會過。更麻煩的是**沒寫的東西**：某層驗證沒做，文件裡就不提，讀的人以為做過了。

**決定**　每項證據要指到 log 行、資料列、截圖或 commit；不適用的驗證層明確記為 skipped 並寫原因。另外要求突變驗證：把關鍵改動暫時還原，測試必須變紅。

**代價**　完成文件變長，寫證據的時間可能和寫程式差不多。但它讓驗收從「相信 agent」變成「檢查證據」。

---

## 8. 先寫完成文件，再精簡狀態

**情境**　狀態檔若保留所有已完成工作的完整內容，很快就大到 agent 每次開 session 都要讀一大堆無關的歷史。

**決定**　`pass` 的工作項在狀態檔只留五欄，完整的範圍、決策、證據移進完成文件。**順序不可顛倒**：完成文件先建立、確認可追溯，才精簡狀態。過程紀錄與計畫同樣在結案時歸檔。

**代價**　結案步驟變多，需要收尾清單才不會漏；驗證器也要檢查「沒有被任何工作項指向的完成文件」這種孤兒。

---

## 9. `blocked` 不得自行恢復

**情境**　agent 看到恢復條件「好像」滿足了，就自己把工作項轉回進行中。有時恢復條件引用的分支或環境早就不存在，條件本身已經失效。

**決定**　恢復需要外部條件滿足**且使用者確認**。恢復條件本身失效時，維持 `blocked`、改寫條件並回報，不得據此判定可以恢復。

**代價**　即使阻礙明顯已解除，也要等人確認一次。

---

## 10. Production 寫入只能依有到期日的具名例外

**情境**　一次性的 production 授權，很容易在後續對話中被延伸解讀成「之前同意過類似的事」。

**決定**　Production 預設唯讀。每次寫入都要登記一筆具名例外，逐項列出授權範圍、**明確不授權**的事項與**硬性到期日**，並固定寫上「不得以本例外推導其他行為」。作廢項目劃線保留，不刪除。

**代價**　每次 production 操作前都要寫一段登記，看起來繁瑣；但事後任何人都能回答「這個變更是誰、在什麼範圍內授權的」。

---

## 11. 產出成果的 agent 不能當唯一評審

**情境**　agent 評自己的成果，傾向用成功的部分抵銷失敗的部分，也傾向把自己的敘述當成證據。

**決定**　評分表規定：缺可定位證據就給 0 分；先列反證再給分；硬門檻失敗不能被其他高分抵銷；自評的 Accept 只算暫定，需要人工或獨立評審確認。評分表本身也要定期和人工判斷校準。

**代價**　里程碑驗收一定要有第二雙眼睛。

---

## 12. Clean state 不等於 `git status` 乾淨

**情境**　為了讓收尾看起來整齊，agent 可能還原、刪除或順手提交使用者自己在做的變更。

**決定**　收尾時先區分本次變更與既有變更，與本次無關的一律保留，不還原、不刪除、不提交。worktree 隔離也讓 agent 不需要碰主檢出。

**代價**　收尾時無法用「工作目錄是否乾淨」這種簡單標準判斷，必須逐項檢查。
