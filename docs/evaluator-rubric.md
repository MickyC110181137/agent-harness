# 成果評分表

在一個工作階段、一組工作階段或專案里程碑完成後，**正式接受成果之前**用本表評審輸出品質。

[Definition of Done](definition-of-done.md) 回答的是「這個工作項能不能結案」；本表回答的是「這批成果的品質能不能被接受」。

## 使用方式

1. 記錄評審範圍、工作項 id、版本或 commit、評審者與日期。
2. **先蒐集證據**（程式碼、文件、命令輸出、測試與行為），再依六個面向評分。
3. 每個面向只能給 0、1、2 分，並附上可定位的證據與反證。
4. 依總分與硬門檻選擇 Accept、Revise 或 Block。
5. 將結論與後續動作記錄於 `progress.md`。

## 證據規則

- 缺少可定位的證據時給 0 分，**不得依 agent 的自述推定通過**。
- 「應該可運作」「看起來正確」與未執行的測試不算證據。
- 每個分數至少引用一項檔案、diff、命令輸出、測試結果或可重現的行為。
- **先列出失敗、限制與反證，再決定給分**；不得用成功項目抵銷硬門檻的失敗。
- **產出成果的 agent 不得作為 Accept 的唯一評審**；自評的 Accept 只能視為暫定，需人工或獨立評審確認。

## 各面向評分標準

### 正確性

- **2**：全部需求與完成條件都有實作及可重現的行為證據，沒有已知錯誤。
- **1**：核心行為可用，但有已記錄的次要缺口、邊界情境或平台差異。
- **0**：核心需求缺失、行為錯誤、與規格衝突，或沒有行為證據。

### 驗證

- **2**：必要測試、預設 gate 與適用的部署後驗證都已執行並通過，命令與結果已記錄。
- **1**：部分檢查通過，但仍有明確且已記錄的環境阻礙、既有失敗或未覆蓋項目。
- **0**：必要檢查未執行、失敗未處理、證據缺失，或以宣稱取代命令結果。

### 範圍紀律

- **2**：只修改所需功能與必要的狀態／文件，所有變更來源清楚，沒有覆蓋他人變更。
- **1**：有少量範圍外變更，但必要、可逆且已明確說明。
- **0**：同時實作多個功能、進行無關重構、修改不明檔案，或覆蓋既有工作。

### 可靠性

- **2**：重新啟動與重跑都成功，狀態可恢復，錯誤路徑安全，沒有資料遺失或資安風險。
- **1**：主要流程可用，但重啟、平台、錯誤路徑或持久化仍有已記錄且可修補的不確定性。
- **0**：無法重啟或重跑、可能遺失資料、存在資安風險，或只在當前工作階段可運作。

### 可維護性

- **2**：遵守專案既定的分層架構，實作最小且清楚，測試與文件足以支援後續修改。
- **1**：可理解且可修改，但有已記錄的架構偏差、重複、缺少測試或文件缺口。
- **0**：跨層耦合、過度設計、命名或責任不清，下一個工作階段難以安全修改。

### 交接準備度

- **2**：狀態檔是唯一狀態來源，過程紀錄、交接快照與文件沒有衝突，下一步可直接執行。
- **1**：大部分狀態已記錄，但仍需少量人工說明或補一項資料。
- **0**：狀態互相衝突、缺少下一步或阻礙資訊，新 session 必須先詢問人員或修復 repo。

## 結論

### Accept — 達到標準

必須**同時**符合：

- 總分 10–12 分。
- 六個面向都沒有 0 分。
- **正確性、驗證、可靠性皆為 2 分。**
- 收尾清單的必要項目全部通過。
- 沒有未記錄的阻礙、資料風險、資安風險或範圍外變更。

### Revise — 修補後再接受

符合任一情況：

- 總分 6–9 分。
- 總分雖達 10 分，但任一面向未達 Accept 的硬門檻。
- 問題可以在不改變核心設計與需求的情況下修補。

必須列出具體的修復項目、負責範圍與重新評審的條件。

### Block — 必須先解決根本問題

符合任一情況：

- 總分 0–5 分。
- 正確性、驗證或可靠性任一為 0 分。
- 存在資料遺失、密鑰外洩、權限繞過或其他重大資安風險。
- 有虛構測試、虛假 `pass`、覆蓋他人變更或無法重現的成果。
- 需求、架構或外部依賴存在根本衝突，無法靠局部修補解決。

## 校準

評分表不是一次定稿，要持續與人工判斷校準：

1. 用本表評估一個已完成的里程碑。
2. 把各面向分數與結論，和人工評審的結果並列比較。
3. 找出分歧，判斷是證據不足、判準模糊、門檻過鬆還是過嚴。
4. **只針對分歧**修改對應的 0／1／2 分標準或硬門檻。
5. 用同一份成果重新評分，確認新規則是否更接近人工判斷。
6. 用不同類型的成果重複測試，直到判斷穩定；**不得只為單一案例調整**。

每次修改本表，都把原因、前後判斷差異與使用案例記錄下來。
